# 2026-09-08：新闻获取、文章质量与编辑效率评估

本轮在实际使用的 Mac 上检查 GitHub 版本、运行服务、用户数据、真实来源和编辑器，并完成第一批修复。判断是：项目已有完整生产链路，但新闻覆盖和证据读取还不稳定，不能仅凭测试通过就称为成熟产品。下一阶段应以“重要新闻是否漏掉、事实是否读全、用户改完一篇需要多久”为验收依据。

## 1. 当前状态与问题根因

检查起点：GitHub `origin/main` 与本地 `main` 同为 `48fcb8a`，没有待拉取的 main 提交；本轮改动位于 `codex/reliability-news-audit`。运行时使用 Node 22.23.2、npm 10.9.8。终端默认 Node 26 不符合仓库约束。

初始数据为 53 个来源配置、30 次采集记录、20 篇存储草稿（包含历史稿）、27 个素材记录。来源数量不等于有效覆盖；素材记录数量也不等于当前文章的可用配图数量。

| 观察到的现象 | 本次确认的原因 | 对日常使用的影响 |
| --- | --- | --- |
| 拉取了新代码，界面仍像旧版 | 正式实例使用的前端构建停留在 9 月 2 日 | 搜索与继续编辑等后续功能没有实际生效 |
| 连续采集有候选，但没有中文速读 | 最近三次普通采集分别有 12、8、12 条候选，中文速读均为 0；旧配置中的 `gpt-5.4` 被当前登录账户拒绝 | 获取和改编故障叠加，容易误认为没有新闻 |
| 切换新模型后仍失败 | PATH 中的 Codex CLI 为 0.134.0；桌面应用自带 0.153.4，新模型需要新版 CLI | 只改模型名不足以恢复生产 |
| 多个官网来源同时漏报 | Gemini、Qwen 等原来依赖 Google News 定向搜索，本机该域名连接超时 | 多个“不同来源”实际上共享一个故障点 |
| 某来源成功后，失败路线不再可见 | 多路线采集只保留成功条目，部分失败未传递到来源健康信息 | 用户会高估覆盖完整性 |
| 不同 Qwen 文章可能被合并 | 去重时去掉整个 URL 查询串，`blog?id=不同文章` 被视为同一链接 | 成功抓到的新闻仍会在后续丢失 |
| 页面刷新像是刚刚读过新闻 | 首页展示视图生成时间，而非采集结束时间 | 旧新闻产生“刚更新”的错觉 |
| 图片有许可却与新闻无关 | 通用 AI 标签、自有素材身份曾足以进入自动兜底推荐 | 相关性被版权可用性替代 |
| 写作记忆误以为用户喜欢更多图 | 图片托盘中的备选图被当成已插入正文的图片 | 自动收图行为污染用户偏好 |
| 只读到标题，却说原文没有交代价格 | 中文速读提示词要求把材料缺项改写成“文章尚未说明” | 把读取能力不足误写成官方披露不足 |

最近的官方小时巡检没有自动生成中文速读，属于已有的延迟生成策略；不能把所有“0 条速读”都算成模型故障。

## 2. 本轮已实现的改动

### 新闻获取与诊断

- Gemini 增加官方产品 RSS；Qwen 增加官网公开文章目录适配器。Google News 保留为补充发现路线。
- Qwen 目录保留原始发布日期、作者、标题与文章永久链接。没有日期的记录不会伪造为当天新闻。其目录内含正文 HTML，真实响应约 4.69 MB，因此只为该适配器设置 8 MiB 上限，普通订阅仍使用原来的限制。
- URL 去重保留文章身份参数，仅去掉片段和已知追踪参数。修复 Qwen `blog?id=` 等链接的误合并。
- 逐路线记录成功、失败、条目数与简明原因。部分成功显示覆盖不足，同时保留成功结果；不会把仍能产出内容的整个来源计作连续连接失败。
- 外部请求同时服从取消信号和超时期限。收到 HTTP 200 的登录页、验证页或不支持的 sitemap 目录索引，会报告格式问题。
- 首页显示真实的“最近读取”时间，以及“原始信息 → 候选”数量。来源页的读取结果可点击展开，手机也能查看原因。

Qwen 协议发现参考了 [RSSHub 的 Qwen 路由](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/qwen/blog.ts)，本项目独立编写解析、校验和治理逻辑，没有引入 RSSHub 代码或运行依赖。官方入口为 [Gemini RSS](https://blog.google/products-and-platforms/products/gemini/rss/) 与 [Qwen 研究页](https://qwen.ai/research)。

### 写作、图片和习惯学习

- macOS 优先使用实际安装的 ChatGPT/Codex 桌面应用所附 CLI，找不到时回退到 PATH；Windows 保留原有解析逻辑。新配置默认使用已经过本机真实请求验证的 `gpt-5.6-sol`，不批量覆盖已有模型设置。
- 速读提示词明确区分“没有读到”与“原文明说未公布”。只有标题或摘要时，解析器将未知项收敛为读取边界，并移除没有正文支撑的编辑判断。这个规则只处理新生成的速读，不覆盖用户文章。
- 自动素材推荐必须匹配事件实体或具体主题；通用 AI 标签和自有图片身份不足以证明相关，将泛化标签放入实体字段也不能绕过检查。发布媒体名称、作者名及社区发现元数据不再作为配图主体匹配依据。
- 写作记忆按实际插入正文的图片 ID 统计密度，图集按实际选图统计；新增备选图库不再被记成用户增加正文配图。旧段落格式保留兼容逻辑。
- 更新 Tiptap、sanitize-html 及其相关锁定依赖，消除本次 npm 审计中发现的已知问题；Mac 服务安装脚本在执行构建和更改服务之前校验 Node/npm。

HTML 依赖更新依据对应的维护者安全公告：[Tiptap](https://github.com/advisories/GHSA-cp6q-959q-f8rh)、[sanitize-html](https://github.com/advisories/GHSA-g8qq-57p8-ggw5)、[qs](https://github.com/advisories/GHSA-4mjr-xmp4-gh2g)。审计为 0 仅表示这次依赖数据库检查没有命中已知告警，不代表完成了全面安全审计。

## 3. 实际验证与能力边界

### 真实来源

在本机直接读取三个官方源，用时约 10.53 秒：

| 来源 | 读取结果 | 仍有的访问缺口 |
| --- | --- | --- |
| Anthropic | sitemap 返回 100 条原始记录，受单路线数量上限约束 | Google News 补充路线超时 |
| Gemini | 官方 RSS 返回 20 条 | 两条 Google News 补充路线超时 |
| Qwen | 官网目录返回 37 篇文章 | Google News 补充路线超时 |

合计 157 条是**原始记录数**，包含历史文章，绝不是“发现 157 条热点”。它证明官方直读可以在新闻索引失效时工作，尚不能证明热点召回率达标。

另外在独立临时数据目录中，通过正式采集 API 搜索 Gemini 的 9 月 2 日至 8 日记录：20 条原始信息 → 6 条日期命中 → 5 条评分后候选 → 5 条中文速读，完整流程约 63 秒。2 条读到了正文，3 条仅有标题。首页将符合补看条件的旧事件放在近七日区域，没有把它们冒充为 48 小时内的新热点。整个测试没有创建用户草稿或发送平台内容。

真实速读暴露的“尚未读取 → 官方未说明”问题已经补入失败回归并修复，新提示词的真实请求也通过。该次模型输出仍出现过重复产品单词，说明请求成功不能替代逐句审读。正文读取也仍存在明显缺口；后续应统计每个来源的正文成功率，不能只统计标题翻译率。

## 4. 下一阶段首先解决新闻覆盖

此节的首批工作已进入 [第二阶段实施与验收](2026-09-08-news-discovery-stage2.md)：70 条离线案例、官方更新直读、代理根因修复、缓存和筛选诊断。下文保留第一阶段制定的目标，不将离线结果等同于实时热点覆盖。

这是最高优先级。后续每次来源改动都要回答：补回了哪些本应被发现的事件，是否增加了噪声，而不只回答“多抓了多少条”。

### 第一批验收资产

建立可版本化的重大事件账本，先人工标注 20 个重要事件及至少 50 个负样本。事件覆盖模型发布、价格/开放范围变化、产品能力更新、重大研究、安全与政策；负样本包含广告、月度汇总、重复转载、微小 CLI 更新、无日期资料与未确认传闻。

每个事件记录：首个可验证公开时间、至少一个事实原文、应进入的时间窗口、首次采集时间、首次聚合时间、首页是否显示、漏报发生在哪一步。候选排序、来源可用性和正文读取率分别计量。固定样本目标为 20/20 重要事件不漏，负样本不能进入重要发布区；这些是下一轮验收目标，当前没有取得这一结果。

| 工作 | 放在哪个模块 | 可交付结果与验收 |
| --- | --- | --- |
| DeepSeek 官方更新直读；补齐 Gemini API 更新路径 | SourceDesk | 有日期与永久链接的真实记录；索引故障时仍可发现；缺日期时明确隔离 |
| 重点来源增加独立读取路径 | SourceDesk | 官方 RSS、发布页/更新记录、官方仓库 Release 互补；两个相同索引查询不算独立备份 |
| 按路线保存 ETag、Last-Modified、最近成功与退避状态 | SourceDesk | 304 不重复解析；失败路线退避不拖慢其他路线；限制同域并发 |
| 记录过滤漏斗 | SourceDesk / StoryDesk | 原始记录、日期过滤、去重、评分淘汰、事件聚合、首页展示均有数量与原因 |
| 重大事件别名与时间线 | StoryDesk | 产品版本写法归一；预告/正式发布分开；旧研究材料不能改变新事件时间 |
| 重点线索先展示、正文与速读继续补齐 | SourceDesk / StoryDesk | 首批结果的等待时间降低，读取范围明确，不因 AI 批次失败清空候选 |

参考 [Miniflux 配置文档](https://miniflux.app/docs/configuration.html) 的轮询、单站限制和调度方式，以及其 [条件请求处理](https://github.com/miniflux/v2/blob/9a774083ab4f61f7d604fb950bdd6aff029824a1/internal/reader/fetcher/response_handler.go)。将这些能力放进现有 SourceDesk，先避免增加额外守护服务。RSSHub 为 AGPL-3.0，若未来直接集成需单独评估许可证与维护成本；当前只研究公开源协议。

正式小时巡检可作为起点。应先测连续运行时的 P50/P95 发现延迟和请求成本，再决定是否对少数重点官方源缩短到 15–30 分钟；电脑休眠、网络中断期间的时间另行记录，不能虚报全天在线覆盖。社区热度只用于发现与排序，不能替代事件原文。

## 5. 文章优化：准确且信息完整，优先于扩写长度

现有 ContentPackage、逐段事实关联、数字核验、局部修补和版本恢复方向正确，继续沿用。但“段落登记了事实 ID”并不能自动证明段落每句话都被该事实支持，模型审查也不能代替原文核对。

下一批真实试用固定为 12 篇：4 篇官方发布、3 篇多来源综合、2 篇社区发现后回查原文、3 篇官方教程/实践。已有试稿可以纳入复核，但不能重复计为本轮新验收。

每篇保留首稿、用户接受的局部补丁、最终稿、耗时和问题分类。重点检查主体、动作、数字、单位、比较基线、开放地区、适用版本、发布时间与授权条件。没有证据的部分进入缺口列表；若补充背景，先采集新证据、生成新的素材包版本，再提出对应段落补丁。

扩写判断依次为：事件是否讲清 → 读者需要的机制/影响/限制是否有证据 → 现有正文是否覆盖 → 未覆盖事实是否值得加入。短而完整的稿件直接通过，长而重复的稿件继续精简；优质原文优先 Curate 或短导读。对用户已编辑正文只能应用精确补丁，并保留接受、拒绝和撤销记录。

记录“选题到可编辑首稿”“用户有效编辑时间”“修正事实错误数”“送稿后返工次数”。首轮测出基线，再以同类文章编辑时间下降 30% 为迭代目标，同时保持未支持事实不能交付。本文不把生成成功率当作文章质量分。

正文提取的下一步是按来源建立金样本：标题、作者、日期、正文、原图、图表、脚注各自验收。可对比现有提取器与 [Trafilatura](https://github.com/adbar/trafilatura) 的结果；只有本项目样本上的收益抵得过 Python 打包与 Windows 维护成本，才引入额外运行依赖。

## 6. 图片：先解决用途和对应关系，再扩充库存

当前 27 个素材记录中，10 个标为 licensed、10 个 owned、7 个 check-required。这是库存标签分布，不能据此声称前 20 张都适用于当前文章或已完成交付期权利检查。

图片选择应由段落需要驱动：产品能力用真实界面/演示帧；性能变化用原始图表并保留坐标、单位、脚注；工作机制用有证据的数据或流程卡；人物访谈使用相关人物现场或肖像。公司 Logo 和通用 AI 图不能证明产品能力，素材不足时留出缺口。

下一步在 PackageDesk / DraftDesk 中保存每张图的“解释哪段事实、视觉用途、为何选择、裁切禁区”。先对五篇真实文章的候选图做人工标注，比较当前实体标签规则与小批量视觉核对；后者只能判断相关性、图表语义和裁切完整性，不能替代版权凭据，也不能从图片猜测未给出的数字。

资产库按可复用需求逐步建设：重点产品界面、官方架构图、正确版本的性能图表、明确授权的公司/人物资料。将原文图、当前版本与过期版本分开，保留来源、作者、SHA-256、许可和平台范围；不为了“有两张图”加入无关生成图。跨系统路径与文件指纹检查继续失败即拒绝。

## 7. UI 与发布效率

本轮沿用已有“今日—原文阅读—草稿—发布”结构，先恢复新构建并使状态可信。后续按使用频率推进：

1. 首页首先回答“有什么值得写、为什么、材料是否足够”；继续编辑保留直达。来源故障给出能展开的原因和对应来源，不要求用户理解 RSS 内部实现。
2. 同一 Story 的原文、关键事实、选图与稿型放在一个连续操作流程；后台自动补齐与真正需要用户决定的事项分开。
3. 写稿界面优先展示正文和下一步动作；仅在存在未支持事实、需要确认的图片权利或连接缺口时强调阻断。统计、运行日志和历史尝试默认折叠。
4. 微信交付仍以草稿箱为主，保留版本和幂等回执。验收三种真实情况：首次新建、修改后更新同一草稿、内容未变时重复同步；再检查手机预览与图片呈现。用户最后在微信后台手动发布。

## 8. 写作习惯与 RAG 的实施顺序

学习系统只学习用户明确接受的表达选择：导语长度、段落节奏、标题组织、术语解释和实际配图密度。自动生成、素材抓取和未接受建议不计为手动编辑。至少五次有效手动编辑后应用，继续允许查看、关闭与删除；学习结果不改事实评分，也不进入事实证据库。

建议先建设本地证据检索，再根据评测决定是否增加向量检索。眼前的主要故障发生在来源获取、运行环境与证据读取阶段，向量库无法找回根本没抓到的新闻。

第一阶段复用现有 SQLite 与冻结快照：

- 原始文档保存 URL、作者、版本、原始日期、读取时间、内容哈希与权利状态；以标题/小节分块，表格和脚注保留关联。
- 事实文库和写作偏好分开检索。外部原文始终是不可信数据；检索结果先作为证据候选，再由 PackageDesk 冻结，不能直接绕过证据门进入正文。
- 先用 FTS5/BM25，加公司/产品别名、版本和时间过滤。中文需要分词或专门的字符索引；默认 unicode61 不能按期望进行中文词语切分，trigram 对不足三个字符的查询也有边界，必须固定中文、英文及混合查询回归。[SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html)
- 建立约 80 个真实编辑检索问题，包含短中文名、版本对比、旧事实失效、图表来源和没有答案的情况；记录 Recall@10、引用正确率、无答案误答率、延迟和成本。

只有关键词检索持续漏掉语义不同但事实相同的材料时，才试验 BM25 + 向量候选 + 小规模重排。Anthropic 的 [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) 提供了上下文分块与混合检索的研究参考；其公开实验收益不能当作本项目收益。当前不部署独立向量数据库、不引入完整 Agent 框架，也不把历史文章里的观点回填成新闻事实。
