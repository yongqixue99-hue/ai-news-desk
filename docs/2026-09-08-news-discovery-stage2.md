# 2026-09-08：新闻发现第二阶段

本阶段完成来源直读、日期与事件身份保护、新闻发现评测、读取缓存、网络环境适配和筛选诊断。重点是减少“本应看到却漏掉”的事件，同时避免把月报、广告、传闻升级成重大新闻。文章与图片方面，本轮修的是更新页证据串段问题，没有将采集成功当作改编质量合格。

## 1. 可重复的发现评测

新增 `npm run eval:discovery`，用固定历史时钟回放 20 个已核实的官方事件与 50 个明确标记的合成反例。调用实际 RSS 解析、采集过滤、评分、Story 聚合及今日推荐函数；每个历史事件保留来源 URL、原始标题、日期、核验说明及短改述。语料在 `server/fixtures/news-discovery-golden.ts`，包含 2024/2025 年模型、产品、价格/开放范围、安全研究与政策事件。

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 正例解析 / 日期合格 | 20 / 20 | 20 / 20 |
| 正例进入候选 | 17/20 | 20/20 |
| 正例形成 Story | 17/20 | 20/20 |
| 正例进入今日精选 | 9/20 | 20/20 |

| 反例误入重要发布区 | 8 | 0 |

额外混合竞争回归将 20 条同型号广告、月报、小更新与传闻放在真实公告之前。修复前真实公告被吞并，修复后仍独立进入精选。另有回归保护安全补丁与已确认的数据泄露，避免把 CVE 小版本修复或标题中的 `leaked user data` 错当普通动态或传闻。

**范围限制：**这测的是输入已获得时的离线解析与推荐能力。RSS 包装是合成的，不能据此声称实时热点召回率 100%，也没有测量原文抽取完整率或模型改写质量。单事件正例不代表在大量真实竞争事件中都能进入有限的首页位置；混合竞争测试是另外一项检查。

## 2. 来源与证据准确性

- [DeepSeek 官方更新](https://api-docs.deepseek.com/updates/) 按原日期下的独立事件读取。[Gemini API 更新](https://ai.google.dev/gemini-api/docs/changelog?hl=en) 按官方日期段读取；同一天多项变更保留为一个日期段，不捏造不存在的逐项永久链接。
- 两个已知官方更新页的锚点参与 URL 身份、候选去重和 Story 聚合。相似标题的不同日期段不会被合并；Qwen 的 `blog?id=` 身份保护继续保留。
- 原文读取严格限定选定日期/事件的小节，标题、日期、正文、表格和候选图片都来自该小节。不能用整页 OG 图或另一日期的价格填补当前事件。锚点失效明确拒绝，不能退回整页历史。
- Gemini 文档属于新闻日期段时，不再误归入常青技术文章。明确 AI 官方更新索引可为新产品名提供主题归属；普通新闻网站仍使用主题筛选。
- Gemini 实网曾返回西班牙语，135 个标题仅有 4 个残留英文日期被识别。请求现在固定 `hl=en` 和英文语言头；明确非英语或日期段识别率不足时拒绝部分成功，保留无语言标签的有效英文兼容。
- 官方 sitemap 的共享 `lastmod` 继续不能冒充发布时间。对无日期的官方线索，每批最多回查 6 页、并发 2，优先发布相关条目，只采信原文明确的 `article:published_time` 或适用 JSON-LD `datePublished`。冲突、缺失、只有修改日期、相关文章日期保持未知；未来日期仍被下游隔离。

日期只有日精度的更新段保留相应元数据。存储的 UTC 零点用于排序与时间窗口计算，不代表官网给出了确切发布时刻。

## 3. 真实网络问题与缓存

本机原有代理可以访问 Google 相关来源，curl 使用了它，但 Node 服务默认直连并超时。对照验证中，仅在 Node 启动时启用已有代理，Gemini API 和 Google News 即返回 HTTP 200；原来的网址、DNS、逐跳重定向与 TLS 校验没有放宽。

新增 `server/start.ts` 启动入口：使用已有 HTTP(S) 代理环境；macOS 没有显式环境配置时，只读系统 HTTP(S) 代理。代理地址与认证值不会写入项目、日志或 LaunchAgent 配置。保留用户绕过规则，并补充 localhost、IPv4/IPv6 回环地址。用户显式设置 `NODE_USE_ENV_PROXY=0` 时尊重关闭。

Node 原生环境代理从 22.21.0 引入，必须在进程启动前启用。项目仍可在 22.16–22.20 启动；这些版本若配置代理会收到升级提示。Windows 的 npm 启动入口使用已有环境变量，不自动导入 Windows 系统代理或 SOCKS/PAC 设置。已有计划任务仍走原独立日志入口，需在任务启动环境中显式配置 HTTP(S)_PROXY 与 NODE_USE_ENV_PROXY=1；未改动其日志锁和任务封装。[Node 22.23.2 官方说明](https://nodejs.org/download/release/v22.23.2/docs/api/cli.html#--use-env-proxy)

每条 RSS/官方目录路线保存 ETag、Last-Modified、上次成功与失败退避状态：

- 304 直接复用已解析记录，更新读取核对时间，保留事件发布日期；没有有效缓存时无条件重试一次。
- 429/503 尊重有界 Retry-After；网络失败指数退避，同站最多两个请求。取消不污染失败计数；退避期间不返回旧条目伪装成新采集成功。
- `.workflow/source-cache/source-routes-v1.json` 是可重建缓存，最多 64 个条目、总量 8 MiB、单条 2 MiB；原子写入。解析错误不会替换有效记录，损坏与磁盘错误不会阻断网络读取。不同请求表示及解析版本使用不同键。
- 这不是永久证据库。证据快照、ContentPackage、草稿、图片指纹和发布回执继续使用原有存储与治理机制。

## 4. 筛选过程与界面

采集共用一个生产函数，保存原始数量、日期合格、关键词命中、URL 去重、评分/主题门槛、事件合并和候选上限。各拒绝原因互斥，拒绝数量之和加候选数必须等于原始数。原始日期回查的确认、未确认和超出核对上限另列诊断，不重复计算为拒绝数。

运行记录可展开查看条件请求、重试时间和筛选原因。读取失败与内容已核对但没有窗口内新闻分开表达；历史运行不伪造之前未记录的原因。手机端以紧凑行展示时间、状态和操作，详情不再依赖横向滚动。首页的证据、稿件状态与展示上限仍是后续筛选，不能把采集候选数量等同于首页数量。

## 5. 下一步

1. 在实际使用中补充重要事件漏报账本，分别记录首次发现延迟、原文成功率和首页去向。尤其检查首页有限位置的真实竞争，以及 sitemap 首批 6 页以外的覆盖缺口。
2. 正文/表格/脚注固定样本评测，推进 12 篇真实文章试用：统计无支持事实、缺失限制条件、用户有效修改与定稿时间。扩写只补冻结证据中值得解释的内容。
3. 为 5 篇文章标注图片与段落事实的关系、版本、图表条件和许可，评估小批视觉复核的收益。缺图仍保留缺口。
4. 微信草稿箱首次创建、更新同一稿和重复同步验收仍需有效连接配置。最终发表始终由用户在微信操作。
5. 在上述基线可观测后，再开展本地 FTS5/BM25 检索评测；向量与重排是否值得引入由本项目数据决定。

本轮没有建立无人值守编程任务，也没有自动发布文章。详细工程与正式运行验收见文末追加记录。
