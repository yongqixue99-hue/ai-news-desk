# 小黑盒交付：连接与用户上传图片修复

## 原因

- 浏览器助手后台发出的 `chrome-extension://…` POST 被本地同源校验误拒绝为 403。扩展已安装、版本正常仍无法连接；原先的单元测试没有经过实际 HTTP 中间件。
- 草稿上传接口把用户主动提供的图片标成 `check-required`，且没有记录交付范围。交付逻辑遇到这条图片错误又跳过自动连接，最终将连接和图片错误一起显示。
- 原连接等待时间为 14 秒，短于 Chrome 后台扩展常见的 30 秒唤醒周期。

## 行为

- 点击“送到小黑盒”时先自动连接，再检查并填入；等待覆盖扩展的正常唤醒周期。
- 用户上传、粘贴或主动通过图片 URL 导入的图片标为 `user-provided`，直接沿用用户的交付选择，不再逐个平台重复确认，也不把它误称为“自有版权”。
- 旧稿只兼容修复明确标有 `local-upload` / `upload_`、尚未作过权限选择的旧上传默认值。明确限制、过期状态、自动采集的来源图不改。图片字节、路径和 SHA-256 核验保留。
- 本地上传图片的通用文件名和“本地上传”内部标签不自动追加到文章；用户写的图注保留。
- 只允许带当前配对凭据的 Chrome 扩展请求写入心跳与任务回执两个接口。其他跨来源修改仍拒绝，不开放通用 CORS。

## 验证

- 回归测试先复现图片重复确认、旧上传兼容、连接等待过短，以及经过真实 Express 中间件的助手心跳 403。
- 修复后真实 Chrome 助手 v0.1.24 自动恢复连接，草稿交付预检无阻塞。
- 从新闻台点击交付，真实小黑盒编辑页完成标题、正文、图片、社区、四个固定话题、所有人可见、不参与创作计划的填入及回执核验。最终发布由用户操作。

## 标题计数修复

交付预检和图文创建原先直接使用 JavaScript 字符串长度，导致小黑盒显示 22/30 的中英文标题被算成 30 字，再加一个汉字就误报超长。现统一使用 `xiaoheiheTitleLength`：与小黑盒编辑器一样，Latin-1 字符占半字，其余 UTF-16 单元占一字，显示总数向下取整；空标题独立检查。文章预检、图文创建和交付面板共用该规则，不截断或改写标题。

已在独立空白小黑盒编辑页核对原题 22 字、增加一个汉字 23 字，以及英文、空格、Latin-1、表情和 30 字边界；测试页清空后关闭，未修改用户稿件。新增回归先复现错误，再验证两种交付形式及图文创建。修复后 `npm test` 1155/1155、编辑评测 22/22、生产构建通过。
