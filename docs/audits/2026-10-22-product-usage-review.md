## 1. 结论

我的判断是：产品仍把过多的流程理解、配置与确认工作交给作者。新的“写作”入口已经落地，但从读到一个来源、自己写文章，到各平台内容和设置都就绪，还存在跳转和能力缺口。这可以解释“功能不断增加，仍不愿意用”的反馈，但本轮没有做真人任务耗时对照，不能把这个判断当作已量化的用户研究结论。

接下来优先交付三个具体结果：

1. 链接、截图、网页选中文字成为当前稿件的参考资料，作者可以立刻继续写；AI 生成是可选动作。
2. 同一个交付面板承载六个平台，自动沿用常用设置；常规路径只需要点击一次交付。
3. 每个平台明确说明实际送达的版本、正文、图片和设置；打开入口、填入编辑器、保存草稿、真实账号验收分别记录。

暂时不扩大资讯来源、AI 工具入口和页面数量。现有采集、聚合、事实冻结、版本恢复和交付幂等继续服务写作。

## 3. 当前真正影响使用的地方

### 3.1 链接起稿仍被绑定在生成流程中

**证据**：`src/App.tsx:112` 的链接起稿跳转到 `workbench`；`src/components/QuickDraftModal.tsx` 初始模式为 screenshot，提交后进入证据复核与成稿。当前隔离界面实测路径：

`写一篇 → 粘贴链接或截图 → 新闻工作台 → 快速生成可编辑草稿（默认截图成稿） → 提取并复核`

这条快捷路径没有“仅保存来源，进入/继续手写”的选择。现有空白起稿可以手写；问题在于把参考资料带入手写稿件的路径仍不直接。不能据此声称所有资料导入功能都不存在。

扩展 `chrome-extension/popup.js:14` 的捕获入口仅在单条 X/Twitter 帖子 URL 下显示；没有通用网页或选中文字的同等入口。这与用户在 X、Linux.do 和其他网页上获取灵感的方式存在距离，也不代表后端网页链接解析只支持 X。

**建议**：在稿件中接收链接、截图和选中内容，立即形成来源卡，保留原始 URL、作者、原文、截图与处理状态。捕获失败仍保留输入，不阻止手写。主动点击“基于资料生成”时再执行现有证据复核、冻结和生成链路；交付时继续遵守事实与图片检查，不能把未经核实的输入自动升格为事实。

**参考**：[Obsidian Web Clipper 的模板与追加资料](https://obsidian.md/help/web-clipper/templates)、[高亮捕获](https://obsidian.md/help/web-clipper/highlight)。

### 3.2 平台入口分成两套，增加理解与操作成本

**证据**：`src/components/DraftWorkspace.tsx:1946` 同层列出“小黑盒 / 微信公众号 / 多平台”；多平台内部又包含小黑盒和微信。`src/components/MultiDeliveryPanel.tsx:17` 在没有已记忆选择时默认勾选百家号。

**建议**：一个面板、六个平台并列；记住用户常用勾选组合。每个平台只展示结果和设置摘要，需要修改时展开。用稿件版本加平台覆盖项组织标题、封面、社区、话题、权限和计划，避免复制出六份独立文章。默认组合首次未确定时允许一次选择，不能为追求“一键”擅自替用户向平台写入。

保留现有自动保存、按平台独立队列、登录等待、失败项重试和未知结果保护。它们已经存在，不应另造一套交付框架。

**参考**：[Postiz 的共用正文与平台差异](https://docs.postiz.com/general/composer/global-vs-per-channel)、[常用设置组合](https://docs.postiz.com/general/settings/reusables)。不照搬其任一渠道校验失败就全部不保存的语义。

### 3.3 六平台契约还没有落实为六平台完整交付

**代码现状**（`server/delivery-batch-types.ts:1`、`src/components/MultiDeliveryPanel.tsx:172`）：

| 平台 | 当前实现声明 | 本轮证据能证明的范围 |
| --- | --- | --- |
| 小黑盒 | 自动填入路径 | 有自动连接、默认社区/话题/计划、图片和回执等实现；本轮未做真实账号逐字段验收 |
| 微信公众号 | 草稿接口路径 | 有幂等新建/更新实现；本轮未做真实账号逐字段验收 |
| 百家号 | 自动存稿路径 | 依赖同步助手；本轮未做真实账号逐字段验收 |
| 知乎 | 自动存稿路径 | 依赖同步助手；本轮未做真实账号逐字段验收 |
| 今日头条 | 仅打开入口 | `automatic: false`，UI 明示不会自动填入，也不计入自动存稿数量 |
| 小红书 | 未列入统一交付枚举 | 不能显示为已接通 |

这里的 `automatic: true` 是代码能力标记，不能等同于产品契约中的“已验收可用”。已读的交付类型、界面和交接文档没有提供六平台逐字段、与当前适配器版本关联的完整真实验收记录；本轮没有据此断言从未有人测试过这些账号。

**建议**：区分“已实现 / 已连接 / 当前版本已验收 / 本次送达结果”。每次交付记录目标账号、稿件版本、平台草稿地址、字段读回和明确缺项。已完成的功能应继续可用，未验收状态如实展示。头条先补齐实际存稿；小红书作为后续适配，不用一个跳转链接冒充完成。优先顺序可以按用户频率安排，六平台仍保持平等地位。

**参考**：[Wechatsync](https://github.com/wechatsync/Wechatsync) 的逐平台过程与回执。其[私有适配器子模块](https://github.com/wechatsync/Wechatsync/blob/a98e42865387285afcc027c61836488748f3b30f/.gitmodules)意味着“29+ 平台”不是可直接移植的完整公开实现。

### 3.4 首次连接仍要求作者理解技术配置

**证据**：`src/components/SocialDeliverySettings.tsx:36–51` 要求进入 Chrome 开发者模式复制扩展 ID、启用 MCP/同步桥接、填写本地 WebSocket 地址和 Token。小黑盒自有扩展、微信接口和外部同步助手又各有连接方式。

小黑盒常规交付已经会自动尝试连接 Chrome，不能再把“每次都必须先点连接”当作当前事实。真正仍可优化的是首次连接、失效恢复以及多种接入方式的统一呈现。

**建议**：普通界面显示“已连接哪个账号 / 需要登录 / 连接组件未就绪”。首次安装、配对集中在一次引导中，能检测的版本、端口、扩展状态自动检测；技术字段留在高级设置。交付自动复用现有登录态，登录过期后续接原任务。浏览器权限和真实登录不能用绕过保护或读取其他程序 Cookie 的方式省略。

### 3.5 作者仍需辨认过多管理状态

**证据**：隔离写作界面同时呈现草稿状态、确认定稿、保存、交付、删除/清空/回收站、编辑/对照/预览、AI 续写，以及“没有冻结素材包”等内部术语。

“确认定稿”服务于独立的学习/版本流程，本轮未发现它是普通交付的必经点击，不能把它算作强制步骤。新建、删除、清空和回收站已经存在，也不应再次声称缺失。

**建议**：正文附近保留标题、正文、保存状态和交付；新建与草稿库入口保持明显。删除、清空、回收站集中到明确的“草稿管理”，避免把用户之前要求容易找到的能力藏没。资料、AI、版本和逐平台设置按需展开。不能续写时说明当前缺什么资料并给出直接入口，不把内部素材包名词交给作者理解。

**参考**：[Ghost 编辑器](https://ghost.org/help/using-the-editor/)、[文章设置](https://ghost.org/help/post-settings/)、[Typefully 草稿属性](https://support.typefully.com/en/articles/8717753-tags-metadata)。

## 4. 下一轮建议只做三个批次

以下是验收目标，不是本轮实测成绩。每批沿用现有模块、先补回归测试，再执行项目规定的验证；最终发布仍由用户在平台完成。

| 批次 | 最小实施范围 | 完成标准 |
| --- | --- | --- |
| A：顺手起稿与继续写 | 空白、来源资料、截图、选题进入同一稿件；链接可仅作为资料；恢复上次写作位置 | 首页一次操作进入可输入的稿件；资料捕获不强制调用模型或生成全文；20 次切换面板不丢正文与撤销记录；重复链接不重复建资料；内部笔记不混入交付正文 |
| B：一个交付入口和常用配置 | 合并重复平台导航；记忆选择和平台预设；把已有保存、检查、连接、上传、填入串成主动作 | 账号已登录、稿件满足要求、常用配置适用时，从编辑页一次点击启动交付；10 篇合成稿常用字段重复填写 0 次；修改一平台标题不影响母稿和其他平台；某平台失败不重建其他平台已成功的草稿 |
| C：实际存稿与可核对结果 | 补头条存稿；验证现有四条自动路径的字段；补版本化验收记录；评估小红书接入 | 对已验收路径，正文、图片及每个适用的平台设置全部一致；平台内补填与重排 0 次；同版本重试不产生重复草稿；未知结果先核对再重试；最终发布接口调用 0 次 |

C 的真实平台验证需要单独的真实操作范围，不能用此次“查看与研究”代替。先用假平台和示例数据覆盖失败、断网、重启、登录过期及字段不一致；真实验收完成后才标为可用。不能为让“一键”看上去成功而吞掉图片失败或事实缺项。

另用同稿同平台对照记录：直接在平台操作与经过工作台分别花多久、点几次、重复填哪些字段、平台内还修几处。优先从已有交付回执和返工记录自动取得数据，避免给作者增加一套必填统计表。当前没有这组对照数字，因此不承诺已节省多少时间。

## 7. 验证边界
