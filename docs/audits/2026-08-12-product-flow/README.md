# AI 新闻工作台产品流审计

审计日期：2026-08-13  
范围：今日工作台、草稿编辑/Agent、新闻源、定时任务、AI 设置、截图/链接成稿、运行记录。  
用户目标：每天从可靠来源发现值得写的新闻，生成有图、有证据、可修改的草稿，再安全填入小黑盒人工发布。

## 总体结论

产品骨架已经成立，当前最需要提升的不是继续增加入口，而是让每个状态都可解释、可恢复、可验证。采集、编辑、AI Agent、配图、扩展填入和人工发布已经形成完整闭环；主要风险集中在路由状态、证据链、图片版权、发布前验证、任务可观测性和无障碍细节。

## 流程步骤与健康度

1. **草稿编辑与 Agent — 良好，但信息密度过高**  
   连续编辑、对照预览、右侧 Agent 和版本/发布工具已经可用。打开 Agent 后同时出现编辑、预览、工具轨与宽抽屉，正文空间被明显压缩；Agent 结果字体多处只有 7–9px。建议用“检查结果摘要 + 问题数”做默认层，详细分析按段折叠，并允许全屏 Agent。

2. **今日工作台 — 良好，但新旧运行语境混在一起**  
   日期、关键词、频道、官网来源、排序与候选表已形成清楚入口；“传播参考不是阅读量”的说明值得保留。页面上方是下一次采集时间，中间参数是下一次手动采集，右侧与底部却展示上一轮运行，容易把“即将执行的配置”和“历史结果”误认为同一任务。建议增加“新建采集 / 当前运行”分层，采集后生成不可变的运行快照。

3. **新闻源管理 — 良好，但缺少维护工具**  
   母站官网、后台接口、用途和健康状态区分清楚。仍缺少按频道、用途和健康筛选，批量启停/默认采集、测试单个来源，以及“最后成功 / 连续失败次数”。删除仅用浏览器确认框，也不适合日后服务器多人使用。

4. **定时任务 — 良好，但配置与基础设施耦合**  
   下次运行、最近一次、睡眠补跑和 Chrome 扩展状态已经透明。日常调度设置与扩展安装教程、CDP 调试、环境健康挤在同一首屏；安装成功后仍长期展示三步安装说明。建议把它拆成“自动化策略”和“发布连接”，连接成功时把教程折叠为维护入口。

5. **AI 设置 — 可用，但模型分工表达复杂**  
   成稿、分析、优化可以分别选择，密钥不写入项目也是正确设计。当前每行同时出现模型能力、密钥状态、两种 Agent 角色、配置与启用，第一次使用较难建立心智模型。建议顶部做三个明确插槽：成稿模型、分析模型、优化模型；厂商列表只负责配置和健康测试。增加“测试连接”、最近耗时、最近错误、估算成本和视觉模型单独选择。

6. **截图 / 链接成稿 — 流程清楚，但缺少中间校对**  
   入口、视觉模型状态、四步处理提示都很清楚。真正的风险是一次提交后直接进入成稿：用户看不到 OCR 识别范围、剔除了哪些导航杂讯、裁出了哪些图片。建议增加 Evidence Review：原截图/网页与清理结果并排，用户可框选正文、取消误裁图片，再生成草稿。

7. **运行记录 — 基本可用，但诊断仍偏日志化**  
   状态、触发方式、范围、原始条目、候选和重试可追溯。大量历史任务平铺在一张长表，缺少筛选、分页/虚拟滚动、耗时和来源失败摘要。建议把运行详情做成抽屉，首层只显示结果和异常原因；把失败来源、过滤漏斗和生成成本做成结构化字段。

## 最高优先级

### P0：修复路由与页面状态不同步

实际审计中，直接从 `#drafts` 导航到 `#workbench` 后，URL 已改变但页面仍显示草稿编辑器，刷新后才正确切换。`App` 只在初始化时读取 hash，没有监听 `hashchange` / `popstate`。这会影响浏览器前进后退、深链接、页面恢复和将来的分享链接。

### P0：建立发布前“真实平台预检”

扩展已经能严格验证填入结果，但验证仍发生在执行填入之后。建议先提供一次只读兼容性检查：编辑器版本、标题/正文上限、图片数、图片描述长度、分区与话题可用性、登录状态、扩展版本。填入后保存一份结构化交付收据和失败截图；页面只在五项全通过时显示“已填入”。

### P1：把文章证据从“文章级”提升到“事实级”

Agent 已经暴露出 sourceSnapshot 只有摘要、草稿却包含大量更强结论的问题。每条关键事实应关联来源 URL、来源段落、采集时间与信心等级。编辑时高亮“仅摘要支持 / 已读取全文 / 多源确认 / 推断”，发布前列出未解决的事实警告。这会比继续增加生成模型更直接地提高文章质量。

### P1：增加截图/链接的证据校对步骤

OCR、杂讯过滤和图片裁切不应是不可见的黑箱。加入“导入 → 清理预览 → 生成草稿”三段式，尤其允许用户取消网页登录区、评论区、广告图和无关头像。

### P1：图片素材库加入版权生命周期

不仅保存图片和标签，还要保存版权状态、来源 URL、授权证据、允许的平台、到期时间、人物/品牌实体和重复指纹。插入草稿后继承这些信息；发布前如果为 `check-required` 必须人工确认。素材库还应支持从一次成功发布中“存为可复用素材”。

### P1：可靠的 AI 执行与成本可见性

每个 AI 任务需要显示 provider、model、skill 快照、输入类型、耗时、重试次数、退出码/错误、token/费用（API 支持时）和可重放 ID。增加 provider fallback 但不要静默切换；必须告诉用户这篇文章最终由谁生成。

## 第二优先级

- 来源预设：模型厂商、主流媒体、游戏媒体、电竞热榜等可保存组合，并显示预估采集覆盖面。
- 个性化推荐：记录“选中、跳过、不感兴趣、最终发布、发布后表现”，让排序逐渐学习你的选择，但始终保留评分解释。
- 多平台适配层：同一篇主稿派生小黑盒、公众号、小红书版本；每个平台独立处理字符、图片、标题、话题和版权规则，不覆盖母稿。
- 草稿生命周期：`候选 → 生成中 → 待核验 → 待配图 → 可填入 → 已填入 → 已发布/搁置`，替代过于宽泛的“成稿”。
- 本地数据管理：状态导出、定时备份、恢复演练、媒体清理、磁盘占用和保留策略；为未来服务器迁移准备 schema migration。
- 通知中心：定时采集成功/失败、发现高分候选、AI 失败、扩展离线都进入一个非打扰式中心，而不是只靠短暂 toast。

## 可见的无障碍风险

- 大量辅助文字为 7–9px，尤其 Agent、来源健康、发布检查和 AI 设置；建议正文/辅助信息最低 12px，关键状态不低于 13px。
- 多个弹窗有 `role="dialog"`，但代码中未见统一焦点陷阱和关闭后返回触发按钮；背景也未明确设置 inert。
- 自定义 tab 切换缺少完整方向键行为；截图弹窗只有 Escape 关闭逻辑。
- 侧栏没有“跳到主要内容”链接；长运行表对键盘与读屏用户成本较高。
- 好的一面：核心按钮有可见焦点样式，状态通知使用 `aria-live`，支持 `prefers-reduced-motion`，主要图标按钮多数已有可访问名称。

截图与 DOM 只能确认可见布局和部分语义，不能据此声称 WCAG 合规；仍需键盘全流程、VoiceOver、200% 缩放和 390px 响应式实测。

## 建议的两轮实施顺序

**第一轮：可信闭环**

1. 路由同步。
2. 事实级证据与发布阻塞项。
3. 发布预检与结构化交付收据。
4. 截图/链接清理预览。
5. AI 任务诊断与模型健康测试。

**第二轮：效率与扩展**

1. 来源组合预设和个性化反馈。
2. 素材版权生命周期。
3. 多平台派生稿。
4. 数据备份、迁移和通知中心。
5. 字体、弹窗焦点、移动端与读屏无障碍回归。
