## 四个里程碑

| 顺序 | 交付内容 | 完成依据 |

| 1 | 首批 3 篇真实图文试稿和问题记录 | 覆盖官方发布、多来源综合、社区发现后回到原文的新闻；逐篇走完选题、冻结素材、生成和人工编辑，记录事实、配图、操作及等待问题 |
| 2 | 重要事件覆盖评测与可解释推荐 | 建立至少 20 个有来源快照的事件案例；应出现的重大事件全部进入相应候选/重要发布位置，重复或过期内容按预期处理，真实访问失败能定位到具体环节 |
| 3 | 原文图片与正文配合质量 | 用至少 5 篇富含图表的来源核对发现范围、下载情况、选图与段落位置；完整图例和来源可追溯，手机能阅读关键数字，缺图有具体原因 |

## 1. 首批真实稿件：建立质量基线

选择一篇可读取的官方模型发布、一篇有独立来源的综合报道、一篇社区链接到原始项目的新闻。已有可用文章优先采用短导读或 Curate，社区材料按原文类型路由。

每篇保存一份简短试用记录：

- 选题与读者需求：用户希望普通读者读完知道什么。
- 原始链接、Story、素材包及草稿版本的对应关系。
- 从选题到首稿的自动处理耗时、人工操作耗时和修改耗时，分开记录。
- 用户删掉的空话、补充的必要信息、事实归属错误及稿型错误。
- 原文相关图片数、已发现数、本地成功数、正文实际采用数；记录未采用原因。
- 具体阻断与恢复方式，包括访问失败、凭据、图片权限和外部平台条件。

先依据这三篇确定基线，再制定合理的节省时间目标。修改必须保留旧稿；编辑类故障先建立失败回归，再修素材、事实映射、稿型或生成规则。

## 2. 重要事件发现：把覆盖、重要性和讨论热度分别验证

先审计现有重点官方来源的实际发现路线及最近成功读取记录。为每条事件记录“源中存在 → 已发现 → 已聚合 → 展示位置”，定位抓取遗漏、错误合并、日期错误和排序问题。来源可访问但确实无更新，应与读取失败分开呈现。

至少 20 个案例需要包含：正式模型发布、新能力开放、重要限制或价格调整、预告与正式发布、旧文更新、同日多个发布，以及 nightly/CLI 日常更新等反例。保存可信发布时间和来源快照，验证新版本名称也能通过事件属性识别，减少对少数型号名称的依赖。

推荐理由分别回答：

1. 事件为什么重要：能力、可用范围或使用门槛发生了什么变化。
2. 为什么适合当前账号：读者需求和用户明确反馈。
3. 有多少可观察的讨论：来自哪些平台、何时采样、增长是否有历史快照支持。

官方发布即使讨论量少，也可因事件价值进入重要发布；热度数据缺失时显示未知。社区线索帮助发现与理解讨论，新闻事实仍回到事件来源。样本与分支门槛继续执行产品合同。

在后续连续试用期间统计首次发现延迟，参考实际配置的读取周期解释结果。费用与来源启用策略沿用用户已有设置，规划本身不增加 API 费用或监控任务。

## 3. 图片：从收集到用对

现有正文配图和图库机制已经存在，下一步通过真实样本评估并修正选择与放置效果。

- 保留原图优先、图表局部截图补充的顺序。识别封面、产品界面、能力示例、评测图、价格表，检查选中的图是否支持对应段落。
- 核对“图展示了什么、条件是什么、是谁测的”；官方自测保留官方归属，图中的未核验数字不能直接变成新的正文事实。
- 检查图注、图例、坐标轴、单位与脚注。宽表在手机上应提供完整图入口；必要的局部裁图保留原图和出处，并检查是否丢失理解所需上下文。
- 在现有图库中完善低成本选图：查看完整图、选用、换图和调整位置。已插入图片与候选图片的状态应清楚。
- 对当前“两篇来源、每篇 16 张原图和 8 张截图、图库 48 张”的边界记录是否触达上限；触达或部分失败时明确提示范围。
- 受限页面沿用已有手工证据导入路线，核对用户提供的图片与来源；未抓到的交互面板、分页或视频内容显示为缺口。

以事先人工标注的相关正文图片清单为分母检查覆盖率。捕获率、正确选图率及正文采用率分别记录，不能因为保存文件多就判定配图质量好。

## 4. 连续试用与公众号交付

累计 12 篇覆盖官方新闻、媒体综合、社区发现新闻、自述工作副本及满足样本门槛的社区观察；可复用前面已完成的试稿，不为凑数量重复生成。

公众号连接条件就绪后，先进行只读连接检查，再用已审核文章执行 3 篇新建及更新验收。每篇核对标题、封面、正文图片、图注、原文链接和手机排版；保留远端草稿标识及回执，确认修改后更新同一草稿、原内容重复同步不产生重复记录。接口暂不可用时可验证现有复制排版通道，但它不能计为接口同步验收。

最终发布由用户在微信后台完成。来源可用、图片已缓存及用户选择配图，不替代交付时的事实和使用权检查。

基于真实试用继续收敛前端：今日页呈现值得处理的题目与继续编辑入口，编辑器聚焦正文、配图和实际阻断，运行细节进入诊断摘要。至少 5 次有效人工编辑并满足现有确认条件后，再验证透明写作记忆；用户可查看、关闭、删除，记忆不能改动事实评分。

## 持续记录的五项结果

| 结果 | 计算或判断方法 |
| --- | --- |
| 重要事件覆盖 | 人工标注案例中正确发现的事件数 / 应发现事件数，另查展示位置与延迟 |
| 推荐采用 | 实际展示后被用户采用的题目数 / 有效展示题目数，记录忽略原因 |
| 人工负担 | 选题、核验、修改和排版的人工耗时分开记录，与首批基线比较 |
| 配图正确性 | 实际采用图片是否支持对应段落，手机可读，图注与出处齐全 |
| 交付可靠性 | 3 篇真实新建、原位更新、重复同步和预览逐项留下可核验结果 |

代码修改仍需通过仓库要求的测试、编辑评测与构建；触及页面交互时增加相关浏览器检查。运行观测与用户试稿使用产品正式接口，破坏性故障注入及恢复演练使用隔离数据。

## 下一轮的具体起点

先收集这三篇试稿的真实修改与采用反馈；技术工作优先推进 20 个重要事件的发现与聚合评测，并把原图里的表格、脚注和测试条件纳入可追溯证据。之后按条件推进公众号的 3 篇实际交付。前端结构拆分、请求合并等维护工作随实际问题推进，成效以编辑体验、恢复能力和测得的加载改善衡量。
