# 2026-09-09：乔木 RSS 对照与产品调整建议

状态：调研结论与实施建议，尚未接入、迁移或实现 Obsidian 插件。用户之前确认的工作台内定稿、微信草稿箱交付和手动最终发布继续有效；主要阅读入口是否调整为 Obsidian，仍待用户选择。

## 判断

Qiaomu AI RSS 在精选资讯、连续阅读、摘录与笔记衔接方面值得直接借鉴。实测公开阅读流已经包含用户指出的 GPT-6、Fable 5.1 相关文章；我们的当前首页未能稳定展示这两项重要事件。这个具体差距已经成立。

它背后还有独立的 QMReader 服务，提供采集、AI 加工、阅读工作台、伴读与公开资产，不能只把竞品理解成一个简单的 RSS 插件。双方在采集、阅读和 AI 改写上的重叠相当大。

我们的证据冻结、图文成稿、局部修改、版本恢复和微信公众号草稿交付已有实现，任务覆盖超过一个发布按钮；但漏报、日期与证据计数、配图语义、学习记录和真实微信交付仍有缺口。这些能力需要证明能减少用户核对与修改时间，才能形成实际产品价值。

建议先保持现有写稿流程，把 Obsidian 作为可选的阅读与资料入口，以具体案例验证互通价值，再决定是否把更多界面做成插件。

## 两个真实案例

本次最新 100 条公开阅读列表中，两项事件都有多篇相关文章。以下是进一步读取正文的两条：

| 事件 | 列表中的文章 | 已读取的结果 |
| --- | --- | --- |
| GPT-6 Astra | Simon Willison 的 [GPT-6 Astra](https://simonwillison.net/2026/Sep/3/gpt6-astra/) | 原文与中文改写均返回；改写正文约 2,283 个字符；翻译接口返回空。 |
| Fable 5.1 | Ben's Bites 的 [Fable 5.1](https://www.bensbites.com/p/fable-51) | 原文与中文改写均返回；改写正文约 2,875 个字符；翻译接口返回空。 |

这些字符数只记录接口返回规模，不是写作质量分数。Fable 样本本身是多主题 Newsletter，改写仍包含原作者制作工具的个人经历；把它用于自己的署名新闻稿时，还需要重新确定选题范围、作者归属和事实依据。

本次证明两项事件在其当前公开阅读流中可见且有中文改写，尚未测得它在官方发布后一小时的发现率、完整历史覆盖或与我们同源盲评的改写质量。Newsletter 的文章日期也不能直接当成模型发布日。

对照我们的失败位置，见 [GPT-6 与 Fable 5.1 漏报核查](2026-09-09-news-miss-cases.md)。

## 插件、服务与目录分别提供什么

1. **Obsidian 插件**：原生阅读界面、原文／改写／翻译切换、个人 RSS、已读收藏、阅读位置恢复、摘录、图片拖入笔记和指定文件夹内的 Markdown 阅读。
2. **QMReader 服务**：采集和后续 AI 加工；还提供网页阅读工作台、文章上下文 AI 伴读、点评以及具有稳定链接的公开阅读资产。公开站点由服务端运行；代码也支持自托管。
3. **精选频道**：本次接口返回 60 条来源配置，其中 37 条 `enabled=true`。这是配置与启用状态，不等于 60 条健康、即时更新的新闻流。
4. **独立博客目录**：插件发行包内实际有 1,342 个目录条目，供用户探索和选择订阅，不会同时采集所有博客。个人订阅上限在该版本为 100 个。

插件 API 文档明确：服务调用全部为 GET，不注册周期轮询，也不请求新的 AI 生成。用户自行添加的 RSS 直接在本机读取，在插件内只提供原文。远端频道可以有服务预先生成的改写；不是所有自定义来源自动获得相同能力。

插件的本地 Markdown 阅读不等于 RAG，更不等于已学习用户风格。QMReader 的相关改写提示词以预设“乔木风格”为主；本次检查未发现与我们已约定的“自动保存修改对照、用户定稿后学习”相当的完整流程。

## 优先借鉴的五件事

### 1. 让重要消息先进入视野

QMReader 后台将 RSS 获取与慢速 AI 加工分离。我们应核查现有管线中哪些阶段仍阻挡候选持久化或可见性：先展示可靠来源的原始标题与处理状态，再异步补中文速读、正文和图片。重要发布识别不能依赖先生成一段 AI 文案。

验收同时包含模型响应慢、模型失败、来源日期缺失和官方标题没有常见发布动词的情况。证据未齐时可以进入待核实列表，成稿与交付门槛继续有效。

### 2. 精选来源与官方核验互相补充

参考其 Newsletter 与作者目录，为我们选取少量有持续信息增量的来源做对照试用，不直接批量启用全部目录。它们用于发现线索、补充解读和帮助发现漏报；官方发布页、发布日志仍用于确认事件身份、日期及核心事实。

同一事件的不同 Newsletter 不能简单算作独立核验。要回到它们实际引用的原文，防止重复转载提高事实分数。直接消费 QMReader 公共内容 API 或用户已有标准 RSS 均可作为接入候选，保持可替换，不能把一种服务当成唯一来源。

### 3. 把阅读过程接到自己的资料库

建议的首版互通是两条边界清晰的通道：

- 用户从 Obsidian 选中文章链接、摘录或指定笔记，将它送入工作台的来源读取与选题流程，保留原始 URL、作者和选中范围。
- 工作台确认定稿后，将 Markdown 与必要图片副本归档到用户指定的 Obsidian 文件夹，保留版本、来源和回到工作台的链接。

阅读摘录继续归属其原作者；未经用户定稿的第三方内容不进入个人风格样本。同步采用稳定标识和明确版本，重复操作不能生成多份，也不能覆盖用户在笔记中的新修改。

### 4. 优化连续操作，而不是增加页面

借鉴频道与文章切换时恢复位置、紧凑列表、按需出现的搜索、专注阅读、快捷键，以及选中文字即可摘录的操作。

我们已有阅读主栏、工作侧栏和折叠诊断，后续沿这些实现继续精简：用户能在同一流程完成看新闻、留资料、选题、进入编辑；技术状态归入可展开详情，真正需要用户处理的事实或交付阻断保持可见。

### 5. 资料积累服务于定稿和后续检索

延续已确认方案：个人定稿与自动生成的修改对照作为首版写作参考，少量样本即可起步。Obsidian 只是可选的文件入口与归档位置；检索和风格应用仍需单独实现、评测。

先修自动保存漏记，再建立定稿版本和参考片段的来源标记。事实证据、他人参考文章、用户定稿承担不同作用，不能把收藏的他人作品学成用户自己的口吻。微信聊天库继续暂缓。

## 实施顺序建议

| 顺序 | 工作 | 验收重点 |
| --- | --- | --- |
| P0 | 修复 GPT-6／Fable 5.1 的日期、筛选、来源去重和恢复补查问题 | 两项真实输入均能经过完整发现流程；日期真实，重复采集不抬高证据，不依赖模型先返回 |
| P1 | 精选来源小批量试用，阅读列表与摘录入口优化 | 与同一批真实重要事件对照；切换不丢位置，读到有用内容后能直接留作写作资料 |
| P1 | Obsidian 选题输入与定稿归档的最小互通 | 一个真实事件完成选题输入、工作台修改、归档；重复操作、图片与用户后续修改可恢复 |
| P2 | 自动修改对照、定稿库与个人写作参考 | 不要求用户手工做对照；确认定稿后才学习；记录采纳、撤销与实际修改时间 |
| P2 | 事实／图像质量复核与真实微信草稿交付 | 使用同一批原文盲评写作效果，完成微信新建、原位更新、重复同步及手机预览 |

P2 不表示已有事实、图片或交付问题可以放行；现有硬阻断继续执行，针对正在使用的文章先处理具体错误。

## 产品形态选择

推荐首先验证 **Obsidian 阅读与积累 → 工作台核实、成稿与定稿 → 微信草稿箱 → 定稿归档回 Obsidian**。

用户进一步询问 Tab 扩写与写作位置。当前建议：直接使用已安装的乔木插件阅读，写作仍在现有工作台，先补文章／选中文本的“送到写作台”入口与定稿归档。两个产品目前尚未自动打通，乔木插件也没有接入我们的 Tab 续写。

后续的“轻量写作插件”与整体搬迁不同：可以让 Obsidian 的写作界面调用现有本地后台，逐步接入 Tab 续写、选中文本改写和草稿交付。需要适配编辑器上下文、中文输入法、过期建议、撤销及版本冲突，不能把复用后台接口描述为零成本完成。

如果用户希望全程停留在 Obsidian，可以再为现有本地服务增加较薄的插件入口或编辑界面，复用已有后台模块。直接搬迁全部工作台会增加界面、进程、跨平台与版本兼容工作，且不会自动解决这次的新闻漏报。

如果实际试用表明“现成阅读器加简单编辑”已经满足用户的产出目标，也应减少自研阅读功能。项目价值以能否让用户稳定在 10–15 分钟实际编辑时间内完成愿意署名的文章来判断。
